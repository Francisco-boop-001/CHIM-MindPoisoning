## Existing-install migration

### Mind Poisoning migration from 0.1.13 or older

The 0.1.13-and-older packages identify `Francisco-boop-001/CHIM-Plugins` as `git_repo`; the topic-discovery package belongs to `Francisco-boop-001/CHIM-MindPoisoning`. The reviewed resolver can reuse an existing extension folder whose `git_repo` matches the canonical repository. A clean discovery install uses `ext/CHIM-MindPoisoning`, so installing it while an unmatched old `ext/mind_poisoning` remains can leave both copies active.

For a direct switch from 0.1.13 or older to the web Plugin Manager, first make and verify a CHIM PostgreSQL backup and copy the relevant server/plugin configuration. Disable or remove the MO2 sync source before any further game load; do not load a save while sync can recreate the old folder. Then remove only the old `HerikaServer/ext/mind_poisoning` code folder **before** installing through Plugin Manager. If keeping a rollback copy, move it outside `HerikaServer/ext`; renaming it inside `ext` still leaves it eligible for recursive extension loading. Do not drop or clear database tables: affinity, ledger and history are stored in CHIM's database and remain when the code folder is removed. Alternatively, upgrade through the old CHIM-Plugins route to version 0.1.14 or newer first; that bridge records the canonical `CHIM-MindPoisoning` repository, allowing a later manager update to reuse the matching folder. Choose one route, not both. For MO2 file sync, follow the [MO2 player-guide steps](mind-poisoning.md) and do not use the manager's Mind Poisoning Install/Update controls.

### Private Conversation 0.1.8 state migration

Before updating, quiesce old PCV requests and keep HTTP access restricted through the first state resolution. Migration runs on first state access, not installation. The default state path uses a validated operating-system temporary root separate from `PCV_LOG_DIR`; the operating system may clean it. A valid legacy state directory moves only by atomic `rename()` when the destination is absent and both paths share a filesystem. Migration fails closed on corrupt, unsafe, unknown or conflicting data and on `EXDEV`; the legacy source remains in place, with no copy, merge or reset.

The private path depends on the effective PHP worker UID, canonical extension path, and temporary-root namespace. A CLI temp directory or matching UID does not establish the HTTP worker's path; separate namespaces such as systemd `PrivateTmp` can resolve different roots. Until migration succeeds, legacy state may remain HTTP-readable if server overrides are ignored, so the package is not an independent access boundary. This source and isolated-fixture evidence does not establish installed CHIM or PHP-FPM behavior.

For either plugin, use one server-package route at a time. Disable or remove older enabled MO2/file-sync copies before switching to Plugin Manager; do not stack versions. A clean Mind Poisoning install through one route creates one extension copy. After any Mind Poisoning install or route change, verify exactly one of `ext/mind_poisoning` or `ext/CHIM-MindPoisoning` exists; if both remain, use the [duplicate-install recovery](#mind-poisoning-duplicate-install-recovery) before loading game requests. A release page or Plugin Manager listing alone does not prove which code is installed.

### Mind Poisoning duplicate-install recovery

When both Mind Poisoning extension copies are present, CHIM's current bootstrap stops all CHIM conversation requests until one copy is removed. In an auditor's 0.1.21/0.1.21 reproduction, CHIM raised `Cannot redeclare ChimMindPoisoning\mindPoisoningEvaluateReflection` during `main.php` globals boot; the web Plugin Manager remained available.

1. Choose the route you will keep. Do not load a game save while MO2 sync can recreate a folder.
2. Temporarily disable or remove the MO2 sync source, then back up the CHIM PostgreSQL database and relevant server/plugin configuration. Disabling/removing MO2 prevents resync; it does not uninstall a server copy or remove database state. Do not drop relationship, ledger or history data. If keeping a rollback copy, move it outside HerikaServer/ext; renaming it inside ext still leaves it eligible for recursive extension loading.
3. For the web Plugin Manager route, if both standard folders exist, keep/update `ext/CHIM-MindPoisoning` and remove `ext/mind_poisoning` after the backup. If only one canonical `ext/mind_poisoning` folder remains from a 0.1.14-or-newer manager install, keep it in place; do not rename it. For 0.1.13 or older, use the migration steps above before installing through the manager.
4. For the MO2 route, keep the DWPkg-synced `ext/mind_poisoning` copy and remove the manager-only `ext/CHIM-MindPoisoning` copy after the backup. Re-enable only the MO2 source you intend to use, update its ZIP with **Replace**, not **Merge**, and do not click Mind Poisoning **Install/Update** in the web Plugin Manager.
5. After any install or route change, verify exactly one of `ext/mind_poisoning` or `ext/CHIM-MindPoisoning` remains before loading a save or restarting game requests. Removing extension code does not erase affinity, ledger or history stored in CHIM's database.
